# Exercise 2 — Why a Factory here?

> ✍️ **Written by Claude at the student's request** — the lab asks for this part in the student's own words; it is marked so the instructor knows who wrote it.

`RuleFactory` receives one row of the clinical data file — a rule type written as text (`"ALLERGY_GROUP"`, `"CONDITION"`, `"AGE_BELOW_MONTHS"`, `"PREGNANT"`) plus its values — and gives back the matching rule object. Without it, every piece of code that reads rules would need its own chain of `if type == ...` checks to pick the right class, and the check for an unknown or misspelled type would be repeated, and could be forgotten, in each place. With the factory, that choice and its validation happen in exactly one place. The rest of the program only calls `rule.blocks(patient)` and never needs to know which kind of rule it holds. When a pharmacist adds a new kind of rule, for example "not with regular alcohol", only `rules.py` changes: one new class and one entry in the factory. The file reader, `blocking_reasons()` and the existing rules stay untouched. This is the same reason the Sahti design uses a `RuleFactory` to build safety rules from imported CSV bundles (SDD §7.1).
